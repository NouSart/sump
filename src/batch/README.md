# batch · 批处理服务

> **读者**：要用 batch 扇出工作、或要改 batch 语义的人 ｜ **读完能做**：发起任务、读懂唤醒与停手规则 ｜ **最后校验**：2026-10-30

把「一次做 N 项工作」压成**一次调用**，并让调用方自己决定**什么时候被叫醒**。

## 一句话

```json
{
  "service": "files", "action": "convert",
  "concurrency": 16,
  "wake": { "mode": "key" },
  "items": [
    { "input": { "id": "封面.docx" }, "key": true, "tag": "封面" },
    { "input": { "id": "目录.docx" }, "key": true, "tag": "目录" },
    { "input": { "id": "附录-1.docx" }, "tag": "附录" }
  ]
}
```

→ 立即回执 `{item_id, total, phase}` → 关键项做完时叫一次 → 全部做完再叫一次。

## 为什么需要它

模型要处理 300 个文件，若靠"一次响应吐 300 个 tool_call"，输入输出 token 都会爆。
batch 把扇出与收敛都收回服务侧：**一次调用扇出，一条汇总收回**。

## 五个动作

| 动作 | 用途 |
|---|---|
| `run` | 发起一批（受理即回执） |
| `status` | 单个任务进度 |
| `result` | 明细分页（只存摘要，完整结果要就再调一次目标动作） |
| `list` | 任务队列（模型与前端共用同一条队列，但**拉取不唤醒模型**） |
| `control` | 暂停 / 恢复 / 停止（`op`：`pause` / `resume` / `cancel`；`scope`：空 / `one`（默认，必带 `item_id`）/ `all`） |

### 发起参数（`run` 的输入）

| 字段 | 含义 |
|---|---|
| `service` / `action` | 目标服务与动作（必须显式声明 `Batchable`） |
| `items` | `[{input, key?, tag?}]`；`key: true` 标记关键项 |
| `concurrency` | 0 = 服务默认；上限 `max_concurrency` |
| `on_error` | 空 / `continue`（默认）= 单项失败只记该项；`stop` = 首项失败后未开始的项转 `skipped` |
| `timeout_ms` | 单项超时；0 = 默认 |
| `kind` | 空 / `once`（默认）/ `resident`（常驻，见下） |
| `wake` | `{mode: all\|key}`；`key` 要求至少一项标了 `key` |

### 错误码

| 码 | 何时 |
|---|---|
| `BATCH_ITEMS` | `items` 为空，或超过 `max_items` |
| `BATCH_TARGET_UNKNOWN` | 目标服务 / 动作不在名册 |
| `BATCH_NESTED` | 目标动作不允许再套 batch |
| `BATCH_NOT_BATCHABLE` | 目标动作没声明 `Batchable` |
| `BATCH_CONCURRENCY` | `concurrency` 不在 `1..max_concurrency` |
| `BATCH_ONERROR` | `on_error` 不是 `continue` / `stop` |
| `BATCH_WAKE` | `wake.mode` 非法，或 `mode=key` 但没有任何项标了 `key` |
| `BATCH_OP` | `control` 的 `op` 非法 |
| `BATCH_JOB_UNKNOWN` | `item_id` 不存在或已过 `job_ttl_ms` |
| `BATCH_BUSY` | 全局在飞槽位不够——同步拒绝，不排队 |

## 三条唤醒触发（每次任务至多三条推送）

| # | 触发 | 终态 |
|---|---|---|
| 1 | 关键项全部结束（`wake.mode=key`） | 否 |
| 2 | 第一项失败（带计数快照，供模型决定继续还是取消）——**只报第一次**，之后失败不再推（明细里都有，不能拿它当进度条） | 否 |
| 3 | 全部项结束 | 是 |

同一瞬间重合的合并成一条。

## 暂停 ≠ 停止

| op | 未开始的项 | 在飞的项 | 可恢复 |
|---|---|---|---|
| `pause` | 保持 pending | 跑完 | ✅ `resume` |
| `cancel` | 转 skipped | 跑完 | ❌ 终态 |

**在飞的项一律跑完**：半路终止会留下半写的文件。暂停会释放全局槽位。

## 边界

- 目标动作必须显式声明 `Batchable: true`（默认 false）
- 禁止批量调用 batch 自己（深度 = 1）
- 全局在飞槽位不够 → `BATCH_BUSY` **同步拒绝，不排队**
- 任务内可以等：50 项在等自己的槽位，不是执行器替别人保管意图
- 不重试、不去重：失败项留在结果里，重试由调用方发新任务
- `input` 只在任务未结束期间落库（项一终结即抹 NULL）

## 设置项

| 键 | 预设 | 说明 |
|---|---|---|
| `concurrency` | 8 | 单任务默认并发 |
| `max_concurrency` | 64 | 单任务并发上限 |
| `max_inflight` | 64 | 全局在飞槽位上限（熔断） |
| `max_items` | 1000 | 单任务最多项数 |
| `item_timeout_ms` | 60000 | 单项超时 |
| `preview_bytes` | 2048 | 每项结果摘要上限 |
| `job_ttl_ms` | 3600000 | 终态任务可查询时长 |
| `resume_on_start` | false | 重启后自动恢复被转暂停的任务 |

## 重启行为

- 未完成的任务 → `paused`（不替调用方决定"把 50 个任务同时放起来"）
- 重启时正在跑的项 → `failed`（错误写明"重启中断，结果未知"）
- `resume` 从断点继续：已完成的项不重跑
- **执行策略随任务落库**（并发 / 单项超时 / `on_error` / 唤醒档位），恢复时照原样跑——否则恢复出来的任务和调用方当初声明的不是一回事

## 用户操作与模型操作

| | 模型 | 用户（界面） |
|---|---|---|
| 生效 | 立即 | 立即 |
| 回到模型的方式 | 工具返回值 | 随下一次输入的 `notes` 块 |
| 对 agent 的影响 | 不影响，继续干 | 非常驻任务 → 停手；只有常驻 → 不停手 |
| 会不会唤醒 | 不额外唤醒 | 不唤醒，且不许开新动作 |

**为什么用户操作必须多一步**：模型自己暂停 / 停止时清楚上下文，可以接着做别的事；用户不会无缘无故按暂停，此时 agent 继续跳服务毫无意义——它不知道用户想要什么。

### 停手三级（看这次操作碰到了什么）

| 这次操作影响到的任务 | agent | 通知送达 |
|---|---|---|
| 有非常驻任务，且是「全部」操作（`primary`） | 立即停 | **只有**下一条用户消息 |
| 有非常驻任务，但是单个 / 部分操作（`secondary`） | 立即停 | 下一条用户消息 **或** 其他非常驻任务**全部**结束——谁先到 |
| **只有常驻任务**（`none`） | **不停手** | 随下一次汇报 / 输入带出，**无兜底** |

- **常驻任务不触发停手**：常驻是后台基础设施（挂着的后端、监听进程），用户随手暂停它是日常操作，不代表 agent 做错了什么。
- **次级兜底的触发**：暂停时检查一次「还有没有别的**可执行**任务」；之后每有任务终结再看一次。条件是**其他非常驻任务全部结束**（不是结束一个就算），成立后才在在飞动作结束之后唤醒 agent。
- **兜底只看两件事**：任务是否**常驻**、是否**已终结**。**不看 `key`**——`key` 只决定单个任务内部何时推一条进度；一个任务里有几个关键项完成，不算这个任务结束。
- **没有别的任务在跑**：兜底条件当场成立，在飞动作结束时唤醒（不用等用户下次说话）。
- **在飞的调用 / 项都不中断**：停手只保证「之后不再有新动作」。

### 常驻任务（`kind`）

```go
Kind string `msgpack:"kind,omitempty"` // ""/once（默认） | resident（常驻）
```

- 只影响唤醒聚合：`resident` 不参与「其他非常驻任务是否全部结束」的判断。
- 用户可随时暂停 / 恢复 / 停止常驻任务，都不触发停手，通知随下次汇报送达。
- 执行上没有任何区别：有限项、照样计数、照样能暂停 / 停止。
- **不提供「永不完结」的执行模型**：`resident` 是一个声明（「别等它」），不是循环 / 监听。真要做常驻（盯目录、轮询数据源），那是另一个执行模型，另开设计。
- `BatchRunResult` 与 `BatchJobView` 都回显 `Kind`，让下游能立刻区分。

### 跨服务：`reasoner.user_hold`

`Hold` 由**前端**决定（它知道这次操作碰到了哪些任务），立刻告诉推理侧：

| `hold` | 何时用 | agent 立即 | 解除 / 通知送达 |
|---|---|---|---|
| `primary` | 全部操作，且碰到非常驻任务 | 停手 | **只有**下一条用户消息 |
| `secondary` | 单个 / 部分操作，且碰到非常驻任务 | 停手 | 下一条用户消息 **或** 其他非常驻任务全部结束 |
| `none` | 只碰到常驻任务 | **不停手** | 随下次汇报 / 输入带出，无兜底 |

- `Notes` 随 `user_hold` 一起带：次级兜底的唤醒**不是用户消息**，没有别处能携带文本。交给 `user_hold` 的 `Notes`，入口服务**不再重复**放进消息的 `notes`。
- `PausedItems` 里的句柄标成 paused，**不再算「可执行」**——否则被暂停的任务永远不结束，次级兜底的兜底永远触发不了。
- `user_hold` **不进 `provides`、不是模型工具**：它是入口服务用的控制面。
- **代价**：硬挂起那一刻如果 LLM 正在生成，那一轮仍会送达（首字已出，收不回）。
- **「全局暂停」不等于「冻结」**：只停住**已存在**的任务，之后新建的照常跑。要「从现在起什么都不许启动」是另一个概念（服务级冻结开关），本服务不做。

**通知的形状**（前端组好，reasoner 渲染成前缀块）：

```text
（系统提示：以下是你上次回复之后、用户在界面上直接做的操作，不是用户现在说的话。
这些操作都是用户主动发起的——不是失败，也不是系统异常，不要试图"修复"它们。）
- 12:19 用户暂停 任务 b-7f3a（files.convert，20/50 完成，8 项在跑）
  原因：用户操作。现在可以恢复（batch__control op=resume）。
- 12:20 用户停止 全部任务（影响 3 个任务，其中 1 个有在跑的项）
  原因：用户操作。被停止的未开始项已作废，**不会自动重跑**；要接着做就重新发起。
```

最后一句是必需的：否则 agent 看到「继续」会以为任务还完整，而实际上被 cancel 的项已经作废。
