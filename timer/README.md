# timer（计时器服务）

**一句话**：AI 说「30 秒后再叫我」，timer 立刻回执，到点把一条补报跳回去——**期间不阻塞任何东西**。

## 动作

| 动作 | 输入 | 输出 | 暴露为 LLM 工具 |
| --- | --- | --- | --- |
| `sleep` | `{ms, note?}` | 受理回执 `{item_id, phase:"queued", fire_at}` | ✅ `timer__sleep` |
| `cancel` | `{item_id}` | `{item_id, status}`（`canceled` / `unknown`） | ✅ `timer__cancel` |
| `list` | `{}` | `{seq, timers:[{item_id, caller, ms, fire_at, note}]}` | ❌（给门户用） |

工具名避开 reasoner 内置的 `wait`。

## 到点怎么把人叫回来（受理即回执 + 补报）

与 shell 同一套 `Provide.Async`：受理回执**立即**返回并闭合调用方的工具配对——不占 pending 表、不扣住模型收尾，期内其它工具照常派发照常回来；到点由 timer 发 `report_result` 跳回**调用方**（信封 `from`）：任务还在跑就注入并唤醒，已收尾就以补报开一轮（结果不丢）。

零阻塞落在两处：处理函数里没有一次 `Sleep`/等待；每条计时一个 `time.Timer` + 回调，长计时与短计时互不影响。撤销也发一条 `final` 补报——调用方的在途记账靠它释放，不能只静默删掉。

**到期可续睡**：再设一次即可（到点补报的文本里也这么提示）。

## 门户倒计时

每次受理 / 到点 / 撤销，timer 把**当前在计时器的快照**（按 `boss` 分组）推给 `-portal <服务名>`（默认 `frontend`）；门户冷启动自己拉一次 `list` 补齐。推的是**快照不是事件**：门户重启、浏览器新开标签拿到的都是当前真相。快照带单调递增的 `seq`——骨架的 `Fire` 各自成 goroutine，**到达顺序无保证**（shell 的测试里实测到过倒序到达），门户只采纳序号更大的；某 boss 的计时清空时会补一条**空快照**，否则那边的倒计时会一直挂着。

## 护栏（满即拒，不排队）

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 下限 | 100ms | 更短没有意义，也顺手挡忙等刷计时 |
| 设置项 `max_ms` | 1h | 可调，**天花板 23h** |
| 设置项 `max_pending` | 64 | 在计时器上限，满即拒 |
| note 长度 | 200 字符 | 超出截断（它会进调用方的模型上下文） |

**天花板为什么是 23h**：调用方（reasoner）的受理登记只活 `asyncJobTTL = 24h`，过期即清、补报到了也会被忽略（只记一行日志）。贴着 24h 设只会造出「看着能设、其实白设」的旋钮，所以留 1 小时余量。要更长的睡眠，得先动调用方的记账寿命。

**计时只在内存**：进程重启即丢，这些计时的调用方不会再收到补报（调用方侧由它自己的 24h 兜底清理）。不假装持久。

## 起

```
go run ./timer -addr 127.0.0.1:9801 -center ws://127.0.0.1:9000/ws -portal frontend
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-addr` | `127.0.0.1:9801` | 监听地址 |
| `-center` | `ws://127.0.0.1:9000/ws` | 设置中心 |
| `-portal` | `frontend` | 门户服务名（推倒计时快照；留空 = 不推） |
| `-max-ms` | `3600000` | 单次计时上限（毫秒；天花板 23h） |
| `-max-pending` | `64` | 在计时器上限 |

`scripts/run-local.ps1` 已包含它。
