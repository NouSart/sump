# 路线与失败条件

> **读者**：想知道「这东西现在到哪一步、下一步该证明什么」的人 ｜ **读完能做**：判断一个需求属于现在做还是以后做 ｜ **最后校验**：2026-10-30

具体的待办项只有一份，在 [TODO.md](../../TODO.md)；本文只讲**顺序**和**什么情况下该停**。

## 1. 三步走

| 版本 | 谁的玩具 | 要证明什么 |
| --- | --- | --- |
| **v1** | 一个人 | 一个人会**天天用** |
| **v2** | 一群人 | 一群人能共享能力而不打架 |
| **v3** | 全世界 | 陌生人能发布和接入能力 |

「玩具」是刻意的，两层意思：**门槛低**（拿起来就能玩，不用读文档）+ **愿意反复玩**（第二天还想打开）。

**顺序不能反**：先做应用，再从里面把架构抽出来发布。若先做架构再找应用，就是纯想象，没人用，也就没有说服力。

## 2. 现在在哪

**做出来的：**

- 一个能完整跑通的产品：门户对话 → 记忆召回 → 调用工具（文件 / 命令 / 图片 / 定时 / 批处理）→ 交付结果
- 13 个独立服务，全栈一条命令启动（见 [../quickstart.md](../quickstart.md)）
- 危险命令默认拦住，等用户点头才执行
- 测试代码比生产代码多（刻意的：基础设施不能靠演示取信）

**还没做出来的：**

- **没有外部用户**
- **跨机没验证过**——离「标准」差这一步
- 没有收入

一句话：**技术已经能证明论点，商业一点没证明。**

## 3. 四条失败条件

一个项目最值钱的部分，是它自己知道什么情况下该停。

| 如果…… | 那就说明 |
| --- | --- |
| 外部开发者没法在一天内接入第一个服务 | 「开放」是假的，整个标准叙事不成立 |
| 作者自己都不愿意天天用 | 留存是零，v2 / v3 全是空中楼阁 |
| 企业客户只想要一个能用的 AI，不在乎谁家的 | 「中立层」没有商业价值，应该去做应用 |
| 大厂把互操作做成免费基础设施 | 位置被填了，需要换位置 |

前两条能在三个月内验证，后两条需要市场反馈。

## 4. 纪律

| 纪律 | 为什么立在前面 |
| --- | --- |
| **先证明，再发布** | 跨机没验证过，就不配为「标准」。早了，就再也收不回来 |
| **先做应用，再抽架构** | 应用里每个能力必须是独立服务，不能为快写死进主流程。写死一次，就抽不出来一次 |
| **不提前做 v3** | 提前做，等于用一个没人用的应用去证明一个没验证的架构——两头都空 |
| **先接受反对，再谈扩张** | 团队只有一种声音，比出错更可怕 |

## 5. 后续阶段（只记方向，不排期）

- **企业治理**：审批策略、SSO / RBAC、多租户、私有模型网关、合规审计——卖的不是功能，是责任。
- **托管云**：一键跑起来的多服务底座（十几个进程的运维是真实痛点）。
- **认证与市场**：服务认证 + 能力市场。

这三层都属于 v2 / v3 阶段，现在做只会摊薄 v1 的验证。**本条不构成排期承诺。**
