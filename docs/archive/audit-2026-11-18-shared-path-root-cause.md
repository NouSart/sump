# 共享库仓库相对路径泄露：根因分析

> **读者**：要修共享库脱敏/审计的人 ｜ **读完能做**：分清直接原因与系统性原因，知道防线缺在哪 ｜ **状态**：分析，问题未修复（跟踪项见 [TODO.md](../../TODO.md)）｜ **最后校验**：2026-11-18

## 结论

这不是「`redact` 少写了一条正则」，而是四层同时缺口：

1. **需求口径没有落到代码**：红线写的是「不得出现可定位到**本机或本仓库**的路径」，实现只认绝对路径（盘符 / UNC / POSIX 绝对路径），仓库相对路径从未被编码。
2. **实现模型选错**：在自由文本上做 regex，没有「仓库」这个上下文；相对路径与普通带斜杠文本难以区分，于是被有意排除在路径规则外。
3. **复检与清洗同源、审计缺类别**：`repair` 复用 `redact` 的谓词，`audit` 只有密钥/熵/长数字四路探针，没有路径探针。两把尺在代码上独立，在**类别覆盖**上同时失明。
4. **验证矩阵缺一类**：测试只造了绝对路径；没有一条「每个仓库顶层目录的相对路径都必须被洗掉」的策略测试，也没有从真实写入路种一条相对路径的端到端用例。

历史迁移是泄露进入共享库的**入口**，但让它长期留下来的，是上面四层。

## 1. 已确认的事实

- `AGENTS.md` 的红线是「跨会话共享库不得出现原文、工具输出、可定位到本机或本仓库的路径、账号或凭据」。
- [TODO.md](../../TODO.md) 记录：`data/experience.db` 现存 15 行含 `src/`、`data/`、`scripts/`、`frontend/` 这类仓库相对路径，其中包含指向 `data/qq-secret.json` 的位置。
- 同一份记录指出：清洗前后都是 15 行。也就是说，清洗工具确实运行了，但**规则没有认出这类形状**。
- 初版清单记成 12 行，漏了 `frontend/` 作为唯一相对路径的行。原因是盘点用的前缀集合是手抄的，不含 `frontend/`。
- 最早的共享库泄露（12 行 `memories` + 117 行 `mem_entries`）来自旧库迁移路径，迁移当时绕过了写入守卫；这是提交 `e47505f` 自己记录的事实。
- 本次分析时工作区没有 `data/experience.db`，因此 15 行的具体内容没有重新读取；本报告只使用 TODO 已记录的计数与代码/提交证据，不复制任何原文。

## 2. 根因链

### 2.1 需求翻译：只实现了「本机」，漏了「本仓库」

`src/memory/redact/redact.go` 的路径规则是：

- `reWinPath`：盘符路径（含正斜杠形态）
- `reUNCPath`：UNC
- `rePosix`：以 `/`、`~`、`./`、`../` 开头的 POSIX 路径

它们共同的前提是「路径有一个绝对起点」。`src/memory/server/server.go`、`data/qq-secret.json`、`frontend/src/...` 没有这种起点，因此一条都不匹配。

红线里的「本仓库」没有对应实现。这是**需求到实现的翻译错误**，不是边界情况。

### 2.2 实现模型：regex 没有仓库上下文

`redact.Text` 面对的是任意自由文本，不知道仓库顶层目录有哪些。相对路径在文本里与普通内容高度同形：

- `and/or`、`TCP/IP`、日期 `2026/11/18` 都含 `/`
- `https://…/src/...` 也含 `/src/`
- 模型总结里的「改了 src/foo.go」与普通叙述没有语法区分

当时的取舍是「至少两段、且以绝对起点开头」，用缩小覆盖面换低误伤。这个取舍本身可以理解，但它没有配套的**校准语料**与**策略矩阵**，于是「本仓库路径」整个类别被静默丢掉。

提交历史也显示路径规则是事故驱动地追加：先有盘符，后来补 Windows 正斜杠，再后来补密钥上下文；每次都在补一个已发生形状，没有回到「哪些类别必须覆盖」重推一遍。

### 2.3 防线同源：清洗与复检用同一把尺

`memory/repair` 明确复用 `redact.Text` / `redact.Detect`。这保证「怎么洗就怎么查」，代价是：

- `redact` 漏认相对路径
- `repair` 清洗也漏
- `repair` 洗完的复检还漏
- 报告自然显示「无命中」

`memory/audit` 被设计成独立的第二把尺，不 import `redact`，方向是对的；但它的探针只有四路：已知凭据、密钥上下文、高熵串、长数字。**根本没有路径探针**。独立实现只保证了「同一类形状不会因为实现相同而一起错」，没有保证「所有红线类别都有探针」。

所以 `-audit` 的 0 应读成「四路探针没有命中」，而不是「库里没有违禁路径」。当前文档没有把这两个语义区分开。

### 2.4 历史入口：迁移绕过守卫

最早的泄露不是新写入造成的，而是旧 `memory.db` 的 `memories` / `mem_entries` 被逐行搬进共享库时没有过脱敏。`e47505f` 后来补了迁移路径的清洗，但：

- 已经进库的行不会因为守卫上线自动消失；
- 守卫补的是绝对路径，相对路径仍然穿过去；
- 之后新写入的相对路径继续积累。

迁移是「怎么进来的」，不是「为什么一直没被发现」。

### 2.5 验证缺口：高覆盖率掩盖了需求缺口

现有测试的形状很一致：

- `redact_test.go` 覆盖 Windows、UNC、POSIX **绝对**路径
- `shared/redline_test.go` 的伪造泄露样本也是绝对路径 + URL + token
- 没有一条 `src/...`、`data/...`、`frontend/...` 的相对路径用例
- 没有一条测试要求「仓库新增一个顶层目录时，脱敏规则必须自动覆盖它」

`redact` 的行覆盖率约 90.8%（见 [2026-11-15 审计](audit-2026-11-15-wishful-programming.md)），但覆盖的是**已写下的分支**，不是「红线要求的类别」。这是覆盖率不能替代需求覆盖的典型案例。

### 2.6 流程缺口：盘点口径与验收信号

两个本可以提前报警的信号没有被当成闸门：

1. **盘点前缀是手抄的**：漏了 `frontend/`。前缀集合没有从仓库顶层目录派生，也没有测试保证「仓库里的每个顶层目录都在扫描范围」。
2. **清洗前后行数不变**：既然已知存在 15 行违例，清洗后仍是 15 行，应当直接判定「规则没匹配」，而不是接受这个结果。缺少「先种一条已知违例，清洗必须改变它」的正向对照。

## 3. 五问（5 Whys）

1. **为什么共享库里有仓库相对路径？**  
   因为写入边界没有把这类形状判定为泄露。
2. **为什么没有判定？**  
   因为路径规则只认绝对起点，而红线要求覆盖「本仓库」路径。
3. **为什么规则只认绝对起点？**  
   因为实现是自由文本 regex，没有仓库上下文；为避免误伤 `and/or`、URL，选择了最窄的绝对路径形态。
4. **为什么测试和复检没抓住？**  
   测试样本只有绝对路径；`repair` 复用同一谓词；`audit` 没有路径探针。三者共享同一个类别盲区。
5. **为什么这个盲区能长期存在？**  
   因为没有「红线类别 → 写入规则 → 独立探针 → 策略测试」的对照矩阵；验收看的是「工具跑完是否报错」，不是「已知违例是否被改变」。

## 4. 影响

- **跨会话泄露**：共享库按设计供其他会话/模型读取，路径会把本仓库结构、目录命名、凭据文件名扩散出去。
- **凭据定位**：`data/qq-secret.json` 这类路径直接指出秘密文件位置；共享库被导出/复制时风险更高。
- **虚假安全感**：`-audit` 报 0、CI 全绿，会让人相信「共享库干净」，掩盖同类形状继续写入。
- **可扩展性风险**：新增顶层目录（如 `automation/`、`deploy/`）不会被现有规则与盘点自动覆盖，下一批泄露只是换个前缀。

## 5. 防复发的设计约束

详细执行项见 [TODO.md](../../TODO.md)，这里只记根因对应的约束：

1. **先定口径再写规则**：明确「仓库相对路径一律算违例」「整段遮还是保留文件名」「是否允许白名单」。没有口径，补正则只会重复事故驱动的循环。
2. **用 tokenizer 而不是万能正则**：按分隔符取 token，再用「仓库顶层目录集合 + 至少两段」判定；先处理 URL，避免把 `https://.../src/...` 当本地路径。
3. **审计必须独立且按类别建探针**：`audit` 不 import `redact`，但必须有一路独立的仓库相对路径探针；`-audit` 的零要能说清「覆盖了哪些类别」。
4. **建立策略矩阵测试**：每个仓库顶层目录的相对路径都必须被 `redact` 洗掉、被 `audit` 报出；顶层目录集合从仓库结构派生，新增目录时测试自动失败。
5. **清洗要有正向对照**：测试里先种一条已知违例，`repair` 预演必须报、apply 必须改变行数、复检必须归零；不接受「前后都是 15 行」。
6. **文档写清语义**：`-audit` 的 0 表示「本版探针覆盖的类别无未裁定命中」，不表示「库里不存在任何违禁内容」。
